버전과 전제 조건

공개 RRA 경로 버전은 /api/v1입니다. 결과 스키마는 standalone-worker-remote-request-status.v1, 대화 스키마는 standalone-worker-remote-request-conversation-session.v1, 워커 간 협업 원장은 standalone-worker-rra-collaboration.v1입니다. 이 버전은 Worker 이미지 버전과 별개이며, 현재 버전 협상 엔드포인트는 없습니다. 전체 인증·첨부·오류 규약과 실행 가능한 Node.js 예제는 RRA v1 연동 개발자 가이드에 있습니다.

외부 프로그램은 대상 Worker의 HTTPS 주소, 관리자가 켠 Remote Request API, 그 Worker가 발급한 시험 API Key가 필요합니다. 개발 워커는 관리자가 설정한 대상 HTTPS origin·Worker/instance ID·RRA 자격을 가진 Worker RRA Connector가 필요합니다. RRA는 일반 Console Chat 세션과 별도 대화 원장을 사용합니다.

  1. 첫 POST /api/v1/requests에는 sessionId를 보내지 않습니다. Authorization: Bearer ...와 Idempotency-Key는 필수입니다.
  2. waitSeconds: 0이면 보통 202를 받습니다. 202 접수 응답에는 현재 sessionId가 없습니다. 응답의 requestId로 GET /api/v1/requests/{requestId}/result를 조회하고, 최종 결과에서 sessionId를 저장합니다. POST가 제한 시간 내 200으로 끝났다면 그 결과에서 읽습니다.
  3. 첫 결과의 terminal: true와 state: completed를 확인합니다. HTTP 200 자체는 업무 성공을 뜻하지 않습니다.

개발 워커가 다른 워커와 이어 대화하기

사용자가 원격 요청을 명시한 같은 Console Chat에서 rra.targets({})로 Connector와 기존 outbound 세션을 확인합니다. rra.preview({connectorId,prompt})는 전송하지 않는 미리보기이며 outboundRequestId와 sessionAnchorId를 반환합니다. 사용자가 Console에서 정확한 대상·내용을 1회 승인한 뒤 rra.status({outboundRequestId})로 첫 요청의 최종 상태를 읽습니다.

후속 요청에는 같은 Console Chat·같은 Connector·첫 sessionAnchorId를 넣어 새 rra.preview를 만듭니다. 호출 Worker가 저장한 대상 remoteSessionId를 대상의 sessionId로 사용합니다. 새 미리보기와 별도의 사용자 승인 후 새 outboundRequestId를 조회합니다. 읽기 전용 대화에서는 rra.preview가 제공되지 않을 수 있습니다.

개발 워커 · 같은 원격 대화에서 두 번 질문
// 같은 Console Chat에서 사용자가 대상 Worker로 두 번 질문하도록 명시한 경우
rra.targets({})
// Connector의 connectorId와 기존 outbound 세션을 확인합니다.

rra.preview({"connectorId":"<선택한 Connector ID>","prompt":"가상 회의 메모의 두 일정을 표로 정리해 주세요."})
// 응답의 outboundRequestId와 sessionAnchorId를 보관합니다.
// Console에서 사용자가 정확한 대상·내용을 확인하고 이 요청을 1회 승인합니다.
rra.status({"outboundRequestId":"<첫 outboundRequestId>"})
// 첫 요청의 최종 상태와 대상 대화 연결을 확인합니다.

rra.preview({"connectorId":"<같은 Connector ID>","sessionAnchorId":"<첫 응답의 ranch-...>","prompt":"앞의 두 일정을 기한순 체크리스트로 바꿔 주세요."})
// 새 outboundRequestId가 생깁니다. Console에서 이 요청도 별도로 1회 승인합니다.
rra.status({"outboundRequestId":"<두 번째 outboundRequestId>"})

개발 워커에게 참조 URL을 줄 때는 이 페이지의 고정 주소 https://manual.workers.dreamlabs.co.kr/guide/rra-session-continuation/를 사용합니다. 사용자 화면에서 승인하는 절차는 다른 워커에 요청하기에 있습니다.

오류와 전달 결과 불명 상태

상태안전한 조치
409 REMOTE_SESSION_BUSY / RRA_REMOTE_SESSION_BUSY같은 대화의 기존 활성 요청을 먼저 조회하고 최종 상태를 기다립니다.
409 REMOTE_IDEMPOTENCY_CONFLICT같은 Key로 다른 본문을 보냈습니다. 원래 제출을 대조하고 새 의미 요청에만 새 Key를 씁니다.
404 또는 anchor mismatch같은 API Key·Chat·Connector인지 확인합니다. 다른 Key의 세션을 읽거나 잇지 않습니다.
delivery_uncertain새 미리보기·재전송을 만들지 않고 원래 outboundRequestId를 rra.status로 대조합니다.
recovery_required / 승인 만료새 대화로 조용히 바꾸지 않습니다. 대상 세션·원래 요청의 상태를 확인하고 사용자 또는 관리자에게 선택을 요청합니다.

HTTP 응답을 잃었다면 원래 Idempotency-Key와 동일 본문을 보존하고 기존 요청의 접수 여부를 먼저 확인합니다. 새 Key로 재제출하면 중복 실행될 수 있습니다. RRA 실행 저장소의 503 REMOTE_REQUEST_EXECUTION_UNAVAILABLE은 대상 이미지에 해당 복구 규약이 적용된 경우에만 기대하며, 대상의 실행 이미지와 버전별 적용 상태를 먼저 확인합니다.

완료 판정과 호환성

최소 확인 기록은 대상 Worker 이미지·API/Connector 설정 revision·확인 시각, 비밀값을 가린 첫/두 번째 요청 ID, 첫/두 번째 최종 state, 동일한 대상 sessionId, 개발 워커라면 동일한 sessionAnchorId와 각 승인 시각입니다. GET /api/v1/sessions/{sessionId}로 실제 메시지 두 쌍을 대조해야 대화가 이어졌다고 판정합니다.

기존 v1의 {"prompt":"...","waitSeconds":0}는 새 대화로 계속 유효합니다. 후속 대화는 선택 필드 sessionId를 추가합니다. 이 문서의 확인일은 API 버전 변경이나 지정 워커 적용 완료를 뜻하지 않습니다. 제품별 변경과 적용 범위는 버전별 개선 이력을 참고하세요.

시작 조건

RRA v1을 켠 승인된 시험 Worker의 HTTPS 주소·시험 API Key 또는 같은 Chat에서 사용할 시험용 Worker Connector가 필요합니다. 대상의 실행 이미지와 설정 revision을 먼저 기록하고 가상 데이터만 사용합니다.

실행 순서

  1. HTTP 첫 POST에는 sessionId를 생략하고 고유 Idempotency-Key를 넣습니다. 202이면 requestId로 결과를 조회해 terminal=true·state=completed와 sessionId를 저장합니다.
  2. 같은 API Key·sessionId, 새로운 Idempotency-Key로 후속 질문을 보내고 두 번째 requestId로 최종 결과를 조회합니다.
  3. 두 requestId가 다르고 sessionId가 같은지, GET /api/v1/sessions/{sessionId}에 user/assistant 메시지 두 쌍이 있는지 확인합니다.
  4. 개발 워커에서는 rra.targets → 첫 rra.preview → Console 1회 승인 → rra.status를 수행한 뒤 같은 Chat·Connector·sessionAnchorId로 새 rra.preview와 별도 승인을 수행합니다.
  5. 첫·두 번째 outboundRequestId가 다르고 sessionAnchorId 및 대상 remoteSessionId가 유지되는지 확인합니다. 전송 결과 불명은 원래 outboundRequestId로만 대조합니다.

통과 기준

HTTP의 후속 요청은 새 requestId와 기존 sessionId를 갖고, 개발 워커의 후속 요청은 새 outboundRequestId와 기존 sessionAnchorId·대상 세션을 갖습니다. 각 요청은 명시적 승인과 최종 상태 대조를 거치며, 첫 요청의 두 가상 날짜가 후속 결과에서 유지됩니다.
