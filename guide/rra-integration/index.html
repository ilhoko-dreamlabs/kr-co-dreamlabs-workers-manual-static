RRA v1과 연동 방식

RRA(Remote Request API)의 공개 경로 버전은 /api/v1입니다. 저장 설정은 standalone-worker-remote-request-api.v1, 공개 요청 상태·결과는 standalone-worker-remote-request-status.v1, 대화 세션은 standalone-worker-remote-request-conversation-session.v1입니다. 이 숫자는 제품 이미지의 릴리스 번호나 콘솔의 v0.1.0 표기와 다릅니다. 현재 공개 API에 버전 협상 엔드포인트는 없습니다.

외부 프로그램 → Worker

관리자가 발급한 RRA API Key로 HTTPS 요청을 보내고 requestId로 결과를 조회합니다. 이 페이지의 HTTP 예제가 해당합니다.

Worker → 다른 Worker

관리자가 설정한 Worker RRA Connector와 서버 제공 rra.* 도구를 사용합니다. Console의 사용자 1회 승인을 거쳐 전송합니다. 아래 개발 워커 절차를 따릅니다.

RRA 세션은 일반 Console Chat 세션과 별도 원장입니다. RRA의 sessionId를 Chat 세션 ID로 사용하지 않습니다.

같은 대화에서 두 번 요청하는 흐름

1 · 시작새 Idempotency-KeyPOST /api/v1/requests
sessionId 생략
2 · 읽기requestId로 결과 조회GET /api/v1/requests/{id}/result
sessionId 저장
3 · 이어가기같은 Key · 같은 sessionId새 Idempotency-Key로 POST
새 requestId 생성
4 · 검증같은 세션의 메시지 확인GET /api/v1/sessions/{sessionId}
user/assistant 두 쌍

요청 ID는 실행 한 건, 세션 ID는 대화 한 줄기, Idempotency-Key는 같은 HTTP 제출의 중복 방지입니다. 세 값의 역할을 바꿔 쓰지 않습니다.

인증과 HTTP 규약

관리자가 대상 Worker에서 Remote Request API를 켜고 API Key를 발급해야 합니다. 기본 설정은 비활성입니다. 외부 호출에는 Authorization: Bearer <RRA API Key>가 필요하며, 모든 새 요청 POST에는 Idempotency-Key가 필수입니다. HTTPS 주소와 Key는 서버별로 관리하고 문서·로그·스크린샷에 원문을 넣지 않습니다.

메서드·경로용도주요 결과
POST /api/v1/requests새 실행 또는 같은 대화의 후속 실행즉시 202, 제한 시간 내 완료 시 200
GET /api/v1/requests/{requestId}상태·세션·메시지 ID 확인200, terminal
GET /api/v1/requests/{requestId}/result결과 폴링진행 중 202, 최종 200
GET /api/v1/sessions현재 Key가 소유한 대화 목록groups[].sessions[]
GET /api/v1/sessions/{sessionId}대화 메시지 조회messages[]
POST /api/v1/attachments파일 사전 업로드201, attachment.attachmentId
POST /api/v1/requests/{requestId}/cancel현재 Key의 활성 요청 취소202

요청 JSON은 prompt(필수), waitSeconds(선택, 생략 시 0), sessionId(선택), attachments(선택, 최대 10개)만 허용합니다. 기본 설정은 prompt UTF-8 64 KiB, 응답 256 KiB, waitSeconds 최대 30초, 활성 원격 요청 1건, 실행 기록 7일 보관입니다. 관리자가 변경할 수 있으므로 대상 Worker의 현재 설정을 우선합니다. waitSeconds는 응답을 기다리는 시간이지 실행 제한이나 자동 취소 시간이 아닙니다. 콜백·웹훅은 v1에 없습니다.

workerId, adapterId, 모델, 런타임, 권한, Wiki 접근 수준, 도구, 작업 디렉터리와 후속 요청 지시는 caller JSON에 넣을 수 없습니다. 권한과 실행 정책은 Worker가 결정합니다.

세션 이어가기: 요청과 응답 읽는 순서

  1. 첫 요청에서는 sessionId를 생략하고 각 제출에 고유한 Idempotency-Key를 보냅니다.
  2. POST가 202이면 requestId와 resultUrl만 받습니다. 현재 라우트 구현의 202 응답에는 sessionId가 없습니다. GET /api/v1/requests/{requestId} 또는 .../result에서 읽어 저장합니다. POST가 200으로 끝나면 응답에 sessionId가 있습니다.
  3. GET .../result를 terminal: true가 될 때까지 조회하고 state와 response를 읽습니다. HTTP 200만으로 성공이라 판단하지 않고 state: completed를 확인합니다.
  4. 후속 질문에는 첫 요청과 같은 API Key와 저장한 sessionId, 새 Idempotency-Key를 함께 보냅니다. 결과의 requestId는 첫 요청과 달라야 합니다.
  5. GET /api/v1/sessions/{sessionId}에서 user/assistant 메시지를 확인합니다. 서버는 같은 Key·세션의 완료된 이전 대화만 제한된 크기로 맥락에 넣으므로 오래된 모든 메시지가 모델에 무한히 들어가지는 않습니다.

202와 200의 차이POST 202는 제출이 접수됐다는 뜻이며 결과가 아닙니다. GET .../result의 202도 계속 실행 중임을 뜻합니다. 최종 200에서는 terminal: true와 state를 읽고, 답변 요약은 response.resultSummary에서 확인합니다. 별도 세션 조회에는 저장된 메시지가 표시됩니다.

복사해 실행하는 Node.js 예제

Node.js 20 이상에서 아래 내용을 rra-continue.mjs로 저장하고, 대상 Worker의 HTTPS origin을 WORKER_BASE_URL, 발급받은 비밀값을 WORKER_RRA_KEY 환경 변수로 넣어 실행합니다. 두 변수의 값은 저장소에 커밋하지 않습니다. 예제는 첫 결과가 완료될 때까지 기다린 뒤 동일한 세션으로 후속 질문을 보냅니다.

Node.js · 첫 요청 → 폴링 → 같은 세션에서 후속 요청
// Node.js 20+ · rra-continue.mjs · 시험용 가상 데이터만 사용
// 실행 전 WORKER_BASE_URL과 WORKER_RRA_KEY를 환경 변수로 설정하세요.
import { randomUUID } from "node:crypto";

const base = process.env.WORKER_BASE_URL?.replace(/\/$/, "");
const key = process.env.WORKER_RRA_KEY;
if (!base || !key) throw new Error("WORKER_BASE_URL / WORKER_RRA_KEY가 필요합니다.");

async function api(method, path, body, idempotencyKey) {
  const headers = { Authorization: "Bearer " + key };
  if (body !== undefined) headers["Content-Type"] = "application/json";
  if (idempotencyKey) headers["Idempotency-Key"] = idempotencyKey;
  const response = await fetch(base + path, {
    method, headers,
    ...(body === undefined ? {} : { body: JSON.stringify(body) }),
  });
  const result = await response.json();
  if (!response.ok) throw new Error(response.status + " " + (result.code ?? "RRA_ERROR"));
  return result;
}

async function completedResult(requestId) {
  for (let attempt = 0; attempt < 60; attempt++) {
    const result = await api("GET", "/api/v1/requests/" + requestId + "/result");
    if (result.terminal) return result;
    await new Promise(resolve => setTimeout(resolve, 2000));
  }
  throw new Error("대기 제한 도달: 기존 requestId로 상태를 다시 조회하세요.");
}

// 처음에는 sessionId를 보내지 않습니다. 서버가 새 RRA 대화를 만듭니다.
const first = await api("POST", "/api/v1/requests", {
  prompt: "가상 회의 메모: 디자인 시안은 10월 5일, 링크 점검은 10월 7일입니다. 두 일정을 표로 정리해 주세요. 외부 도구나 파일은 사용하지 마세요.",
  waitSeconds: 0,
}, randomUUID());
const firstResult = await completedResult(first.requestId);
if (firstResult.state !== "completed") throw new Error("첫 요청: " + firstResult.state);
const sessionId = firstResult.sessionId; // 202 응답에는 없으므로 결과에서 읽습니다.
if (!sessionId) throw new Error("sessionId가 없습니다. 서버 버전을 확인하세요.");

// 새 요청 ID와 새 Idempotency-Key를 사용하고 sessionId만 이어받습니다.
const second = await api("POST", "/api/v1/requests", {
  prompt: "앞에서 정리한 두 일정을 기한순 체크리스트로 바꾸고, 각 날짜를 그대로 유지해 주세요. 외부 도구나 파일은 사용하지 마세요.",
  waitSeconds: 0,
  sessionId,
}, randomUUID());
const secondResult = await completedResult(second.requestId);
const conversation = await api("GET", "/api/v1/sessions/" + sessionId);
console.log(JSON.stringify({
  sessionId,
  firstRequestId: first.requestId,
  secondRequestId: second.requestId,
  firstState: firstResult.state,
  secondState: secondResult.state,
  messages: conversation.messages.map(({ role, status, content }) => ({ role, status, content })),
}, null, 2));

실서비스에서는 HTTP 전송 전에 Idempotency-Key를 로컬의 안전한 기록에 저장하고, 응답을 잃으면 같은 Key·같은 요청 본문으로만 재조회/재전송하세요. 새 의미의 후속 질문에는 새 Key가 필요합니다. 이 예제는 자동 재시도를 하지 않습니다.

첨부파일을 사용할 때

요청 본문에 파일 원문을 넣지 않고 POST /api/v1/attachments로 먼저 업로드합니다. fileName, 허용 mimeType, 정규 Base64 contentBase64와 필요하면 원본 바이트 수 size를 보냅니다. 아래 aGVsbG8=는 안전한 샘플 문자열 hello의 Base64입니다. 응답의 attachment.attachmentId를 attachments: [{"attachmentId":"..."}]로 제출합니다. 업로드와 요청은 같은 API Key여야 하고, 이미 다른 요청에 묶인 첨부를 새 요청에 다시 사용하지 않습니다.

HTTP · 첨부 업로드와 참조 예시
POST /api/v1/attachments HTTP/1.1
Authorization: Bearer <RRA API Key>
Content-Type: application/json

{"fileName":"sample.txt","mimeType":"text/plain","contentBase64":"aGVsbG8=","size":5}

// 201 응답의 attachment.attachmentId를 다음 요청에 사용
{"prompt":"첨부한 시험 텍스트를 읽고 한 문장으로 요약해 주세요.","attachments":[{"attachmentId":"<att-...>"}]}

허용 형식은 TXT/Markdown/CSV/JSON/PDF/PNG/JPEG/WebP입니다. MIME 유형과 확장자를 모두 검사하며 실제 크기 한도는 Worker의 현재 업로드 설정에 따릅니다.

상태·오류·안전한 재시도

응답뜻과 조치
200 + terminal: truestate가 completed인지, blocked/failed/cancelled인지 구분합니다. HTTP 성공이 업무 성공은 아닙니다.
400 REMOTE_REQUEST_INVALID필수 필드·길이·ID 형식·허용되지 않은 필드를 고칩니다. 잘못된 Authorization 형식도 400이 될 수 있습니다.
401 REMOTE_API_KEY_INVALID / 403 REMOTE_API_DISABLED 등Key 또는 API 활성·만료 상태를 관리자에게 확인합니다. Key를 URL이나 로그에 붙이지 않습니다.
404 REMOTE_REQUEST_NOT_FOUND요청·세션·첨부가 없거나 현재 Key가 소유하지 않을 수 있습니다. 다른 Key의 세션 존재 여부는 드러나지 않습니다.
409 REMOTE_SESSION_BUSY같은 세션에 활성 요청이 하나 있습니다. 기존 요청을 조회해 종료된 뒤 새 의미의 요청을 다시 결정합니다.
409 REMOTE_IDEMPOTENCY_CONFLICT같은 Idempotency-Key에 다른 본문을 보냈습니다. 기존 요청을 확인하고 새 요청이라면 새 Key를 사용합니다.
429 REMOTE_INGRESS_SATURATEDWorker 수용량이 찼습니다. Retry-After를 따르고 원래 요청의 처리 여부를 먼저 확인합니다.
503 REMOTE_EXECUTION_DISABLED대상 Worker의 실행이 꺼져 있습니다. 운영자 확인이 필요합니다.

결과 상태는 accepted, running, completed, blocked, failed, cancelled 및 보존/복구 상황의 expired, reconciliation_required를 포함할 수 있습니다. 불확실한 전송에는 새 Idempotency-Key를 만들지 말고 같은 Key·같은 본문의 기존 제출인지 확인합니다. reconciliation_required는 결과 원장을 읽어 대조한 뒤 판단합니다. 모델이나 클라이언트가 임의의 자동 후속 실행을 만들지 않습니다.

개발 워커가 다른 워커에 요청할 때

Worker 내부 개발자/개발 워커의 협업은 이 HTTP 예제를 셸에서 직접 보내는 방식이 아니라 서버가 제공하는 Worker RRA Connector를 사용합니다. 관리자가 대상 URL·Worker 식별·쓰기 전용 자격을 설정해야 하며, 스킬 설치만으로 연결이 생기지 않습니다. rra.targets로 대상을 찾고, 사용자가 명시적으로 요청했을 때 rra.preview로 한 요청을 준비합니다. 실제 전송은 Console에서 사용자가 그 미리보기를 1회 승인한 뒤 이루어집니다. rra.status로 기존 보낸 요청을 조회합니다.

같은 대상 대화를 이어갈 때는 서버가 보유한 session anchor를 사용합니다. 후속 의미 요청은 새로운 outbound 요청 ID·멱등성 키·미리보기·승인을 갖고, 대상 측 sessionId만 이어갑니다. 승인 만료, delivery_uncertain, 대상 세션 분실에서 임의의 새 대화를 만들거나 중복 전송하지 않습니다. 사용자용 조작은 다른 워커에 요청하고 결과 이어받기에 있습니다.

호환성과 확인 범위

기존 v1의 {"prompt":"...","waitSeconds":0} 본문은 계속 새 세션을 만드는 방식으로 유효합니다. sessionId와 attachments는 선택 필드입니다. 이전 설계 문서의 접수 응답 예시에는 세션 ID가 있으나, 202 응답의 현재 구현은 requestId·resultUrl 중심입니다. 통합 코드는 POST 응답에 세션 ID가 즉시 있다고 가정하지 말고 상태/결과 조회로 얻어야 합니다.

이 페이지는 2026.10.21 소스 커밋의 라우트·입력 계약과 대화 서비스 및 기존 계약 검사를 기준으로 작성했습니다. 신규 운영 API 호출이나 새 Console 화면을 이번 문서 작업에서 실행·촬영하지 않았습니다. 실제 대상 Worker마다 실행 이미지, API 설정·Key 상태, 두 요청의 requestId/sessionId, 메시지와 결과를 검사해 기록하세요. 제품 이미지 변경 내역은 버전별 개선 이력에서 확인합니다.

시작 조건

RRA v1이 켜진 승인된 시험 Worker의 HTTPS 주소와 그 Worker가 발급한 시험 API Key가 필요합니다. 가상 회의 메모만 사용하고 키 원문은 공개 기록에 남기지 않습니다.

실행 순서

  1. 첫 POST에 sessionId를 생략하고 고유 Idempotency-Key를 넣어 제출합니다. 202 응답이면 requestId로 결과를 폴링해 sessionId를 저장합니다.
  2. 첫 결과가 terminal=true, state=completed인지 확인합니다. 같은 API Key·같은 sessionId와 새 Idempotency-Key로 후속 질문을 제출합니다.
  3. 두 번째 요청이 종료되면 두 requestId가 서로 다르고 sessionId는 같은지 확인합니다. GET /api/v1/sessions/{sessionId}에서 user/assistant 메시지 두 쌍을 확인합니다.
  4. 같은 Key·같은 본문의 멱등성 재조회와 같은 Key·다른 본문의 409 충돌을 격리 시험에서 확인합니다. 다른 Key의 세션은 읽거나 이어갈 수 없어야 합니다.

통과 기준

후속 응답은 첫 대화의 가상 날짜 두 개를 이어받아 기한순으로 정리합니다. 각 의미 요청의 requestId와 멱등성 키는 다르지만 sessionId는 같습니다. 202만으로 완료를 판정하지 않으며 다른 Key의 세션은 노출되지 않습니다.

남길 증거

대상 Worker 이미지·설정 revision·확인 시각, 비밀값을 제거한 HTTP 상태·스키마 버전, 두 requestId와 sessionId, 메시지 역할·상태·결과를 기록합니다. 이 절차는 운영 통과 기록이 아니라 재현 검사입니다.
