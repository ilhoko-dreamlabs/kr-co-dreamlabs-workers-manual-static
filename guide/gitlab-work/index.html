앞선 GitLab REST fallback 이미지 기준이 안내는 해당 이미지를 실제로 실행하는 워커에서 시험할 기준입니다. 빌드·격리 검사·Registry 등록·서버 배치와 18:37(KST) 업데이트 제안까지 확인했습니다. 그 시점에 새 이미지 적용은 없었고 이후 실행 이미지·실제 GitLab 응답은 미확인입니다. 같은 날 별도 제작된 GitLab·GitHub 계정 권한 방식 이미지는 신규 연결·기존 관리자 전환·OAuth 권한 기준이 다릅니다. 이 이전 이미지의 기능을 새 이미지의 운영 결과로 보지 마세요.

사용 가능 범위 확인하기

GitLab 작업 전에 사용할 워커의 실행 이미지와 계정·프로젝트 권한을 확인합니다. 이 앞선 이미지에서는 준비된 Connector가 있으면 그 경로를 먼저 사용합니다. Connector가 준비되지 않은 경우에도 서버에 설정된 자격과 독립적인 승인 검사가 통과해야만 REST 경로를 사용할 수 있습니다. 기존 기능·외부 리소스 제한과 계정·프로젝트·읽기 전용·비활성·회수 제한을 확인하세요. 후속 계정 권한 방식 이미지에서는 Git 연결 사용법에 따라 서비스가 실제 부여한 외부 권한과 워커 사용 위치를 구분합니다. 사용자는 토큰을 대화에 붙여 넣지 않습니다.

읽기 전용 요청으로 시작하기

권한 있는 시험 프로젝트를 지정한 뒤 다음과 같이 요청합니다. 실제 경로·프로젝트 이름은 자신의 권한 범위에서만 사용하세요.

읽기 전용 시험 요청 예제
내가 접근할 수 있는 시험 GitLab 프로젝트의 열린 merge request 목록을 읽고 제목·상태·링크를 표로 정리해 주세요. 생성·수정·댓글·파일 저장은 하지 마세요. 접근할 수 없다면 이유와 확인할 설정만 알려 주세요.

목록 수와 항목 하나의 제목·상태를 GitLab의 원본과 대조합니다. 일반 GET 요청은 읽기 전용으로 처리돼야 하며, 읽기 시험이 이슈나 커밋을 만들어서는 안 됩니다.

결과와 경로 확인하기

응답 카드가 나타나면 Task의 최종 상태를 확인하고, 실제 프로젝트·자료·링크가 요청한 범위와 일치하는지 봅니다. 운영 진단에서 준비된 Connector 사용, 승인된 REST 대체 경로 사용, 제공자 거부를 구분합니다. 대체 경로가 사용됐다는 문장만으로 자격이나 프로젝트 권한이 충분했다고 추정하지 않습니다. 해당 워커의 실제 GitLab 결과와 함께 판정합니다.

변경 요청 전 확인하기

이슈 생성이나 설명 수정처럼 자료가 바뀌는 요청은 대상 프로젝트·리소스·변경 내용을 먼저 확인하고, 권한 있는 시험 데이터에서 명시적으로 승인한 뒤 한 번만 보냅니다. 결과가 정상이라면 생성된 식별자·링크와 실제 GitLab 자료를 대조합니다. 제공자 권한이 없거나 읽기 전용 계정이면 변경은 거부돼야 합니다. 이 매뉴얼의 읽기 예제는 쓰기 승인을 제공하지 않습니다.

실패와 결과 불명 다루기

로컬 선택·자격 저장소 문제는 워커 설정과 배정 상태를, 제공자 거부는 해당 계정과 프로젝트 권한을 운영 담당자와 확인합니다. 처음 경로가 변경 효과 없이 끝났다고 확실할 때만 승인된 다른 경로를 한 번 사용할 수 있습니다. 쓰기의 결과가 불명확하면 원래 Task와 대상 리소스의 현재 상태를 조회하고, 같은 변경 요청을 자동·수동으로 반복하지 않습니다. 세션을 다시 열거나 워커가 재시작해도 이미 효과가 난 요청을 새 변경으로 해석해서는 안 됩니다. 차단 결과 확인 방법을 참고하세요.

스킬·RRA와 권한 구분하기

번들 gitlab-work 스킬은 작업 순서와 안전한 결과 확인을 안내합니다. 스킬이 보이거나 선택돼도 GitLab 인증·프로젝트 권한·쓰기 승인이 생기는 것은 아닙니다. RRA로 시작한 작업도 원 요청자, 대상 워커, 허용 범위를 확인한 뒤 결과를 기록합니다. Wiki 문서 역시 권한을 부여하지 않습니다.

화면 증거

새 이미지의 실제 화면 미촬영입니다. 이번 후보에는 새 Console UI가 없습니다. 적용 후에는 기존 세션의 읽기 요청·최종 상태·오류와 스킬 선택을 데스크톱과 좁은 화면에서 실제로 촬영하고 워커 이미지·시각·GitLab 결과에 연결합니다. 과거 화면을 후보 실행 증거로 표시하지 않습니다.

시작 조건

10월 19일 후보를 실제로 실행하는 시험 워커와 접근 승인된 시험 GitLab 프로젝트가 필요합니다. 서버 배치와 18:37(KST) 관리 워커 8개의 제안까지 확인됐지만 새 이미지 적용은 그 시점에 없었습니다. 실제 실행 이미지를 새로 확인하기 전에는 기능 검사를 미실행으로 남깁니다.

실행 순서

  1. 정확한 워커 이미지·건강과 시험 계정·프로젝트·읽기/쓰기 범위를 확인합니다.
  2. 본문의 읽기 전용 merge request 목록 요청을 한 번 실행하고 최종 Task·실제 GitLab 항목을 대조합니다.
  3. 준비된 Connector가 있으면 우선 사용되는지, 준비되지 않은 경우 승인된 서버 자격 경로만 사용되는지 비공개 진단과 결과를 비교합니다.
  4. 범위 밖·사용 중지·회수·읽기 전용 계정의 변경 요청이 거부되는지 승인된 격리 환경에서 확인합니다.
  5. 명시적으로 승인된 시험 변경만 한 번 실행하고 결과 식별자와 제공자 자료를 조회합니다. 결과 불명 쓰기의 재전송은 하지 않습니다.

통과 기준

읽기 요청은 자료를 바꾸지 않고 프로젝트 범위의 실제 결과를 반환해야 합니다. 대체 경로도 승인된 계정·리소스 제한을 지켜야 하며 결과 불명 쓰기와 재시작 후 중복 변경이 없어야 합니다.

남길 증거

워커·정확한 내부 이미지·시각, 시험 프로젝트·계정 범위, Task/제공자 결과, 선택 경로·거부 원인·기존 리소스 조회와 실제 화면을 비공개 기록에 남깁니다. 공개 캡처에 토큰·내부 주소를 넣지 않습니다.
