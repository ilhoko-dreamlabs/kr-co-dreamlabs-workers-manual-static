시작 조건과 연결 ID

관리자는 가상 시험 계정, 연결을 만들 공급자/인증 방식, 기존 연결 ID와 revision, 원복 방법을 준비합니다. 일반 사용자는 연결 목록과 허용된 현재 대화 선택을 읽을 수 있지만 연결 생성·자격증명·정책 편집은 관리자 전용입니다. 같은 공급자와 같은 표시 이름을 가진 연결도 각각 다른 연결 ID입니다. 이름만으로 대상을 고르지 않고 ID·공급자·상태를 함께 확인합니다.

저장 상태가 준비됨이더라도 현재 제공자 계정 조회·리소스 접근·모델 실행 성공은 아닙니다. 화면의 편집/저장 동작은 서버 소유 revision을 대조하고 결과를 다시 읽을 때만 완료로 기록합니다.

연결 목록 조회와 새 연결 추가

  1. 설정 → 커넥터 → 연결 목록을 열어 공급자, 표시 이름, 정확한 연결 ID와 기록 상태를 읽습니다. 목록 새로고침은 저장된 메타데이터 조회이며 공급자 인증을 새로 시도하지 않습니다.
  2. 관리자는 새 연결 추가에서 등록된 공급자·인증 방식·연결 이름을 고릅니다. 같은 이름이어도 별도 ID가 생성되므로 의도한 대상인지 확인하고 연결 추가를 한 번 선택합니다.
  3. 생성 응답만으로 완료로 판단하지 않고 목록을 다시 읽어 새 ID가 정확히 한 번 추가됐는지 확인합니다. 결과가 불명확하면 같은 추가 요청을 재전송하지 않습니다.

연결 생성은 인증 대기 상태를 만들 수 있습니다. 토큰·OAuth 승인·사용 위치 정책은 이어서 별도로 설정해야 합니다.

GitLab·GitHub 인증

GitLab 설정은 이 Worker의 모든 GitLab 연결이 공유하는 HTTPS 서비스 origin과 선택한 연결 ID의 write-only Access Token을 분리합니다. origin에는 경로·query·사용자 정보를 넣지 않습니다. 시험용 변경 뒤 origin revision과 연결 revision을 각각 다시 읽습니다. 토큰 원문은 화면에 다시 표시되지 않습니다.

GitHub OAuth 연결은 정확한 ID를 선택해 브라우저 인증 또는 기기 인증을 명시적으로 시작합니다. 기기 인증 중에는 제공자의 확인 주소와 사용자 코드를 본인 브라우저에서만 다루고, 상태 조회·기기 polling·취소를 구분합니다. OAuth 동의 대기 중이라는 표시는 성공이 아닙니다. 기존 연결의 재인증에서는 PAT 교체와 OAuth 시작/상태/취소를 별도로 처리하고, 실패·거부·취소 후 기존 자격의 보존 여부를 읽습니다.

기존 Git 연결을 서버 권한 그대로 사용 방식으로 전환하려면 정확한 대상을 확인합니다. 알려진 OAuth scope 정보, 알 수 없는 scope, 실제 작업 권한은 다른 개념입니다. 같은 연결 ID와 새 권한 상태를 canonical 재조회한 뒤에만 전환을 완료로 기록합니다.

Google Workspace·Apps Script

Google Workspace의 선택한 연결 ID에서 서버가 계산한 동의 scope를 먼저 검토한 뒤 브라우저 승인을 시작합니다. 필요한 Apps Script scope profile이 없으면 승인 시작이 차단됩니다. 승인 상태 조회·취소와 실제 Google 리소스 호출은 별개입니다.

Apps Script 설정은 공통 Google 애플리케이션 scope와 특정 연결의 deployment:function 묶음을 나누어 저장합니다. 한쪽 변경이 다른 연결의 자격이나 리소스 묶음을 바꾸지 않는지 revision·재조회로 확인합니다. 저장된 설정은 승인·스크립트 실행 성공의 증거가 아닙니다.

연결 상태·계정 확인·정보 수정

  1. 관리자는 선택한 연결에서 연결 상태를 새로고침해 로컬 기록을 읽습니다. 이 읽기는 공급자 요청이 아닙니다.
  2. 계정 확인을 명시적으로 실행하면 한 번의 공급자 계정 조회를 수행합니다. 원래 공급자의 401/403과 Console 자체 인증의 401/403을 구분합니다. 실패했더라도 과거 성공 기록을 현재 성공으로 표시하지 않습니다.
  3. 연결 정보 수정에서는 표시 이름을 바꾸고 Google 연결에만 해당되는 기능/리소스 제한을 편집합니다. ID·공급자·인증 방식·상태는 읽기 전용입니다. 저장하지 않은 변경을 버릴 때는 별도 확인을 거치고, 저장 뒤 같은 연결의 revision·값을 다시 읽습니다.

연결 해제와 구성 삭제

연결 해제·삭제 화면에서 정확한 연결 ID, 자격증명 존재, 바인딩 수와 진행 중 인증 여부를 읽습니다. 아직 만료되지 않은 인증이 있으면 먼저 재인증 화면에서 상태를 확인하거나 명시적으로 취소합니다. 연결 해제 확인은 Worker 자격증명과 바인딩을 제거하고 구성은 남깁니다. 그 후 연결 구성 삭제 확인은 남은 설정만 삭제합니다. 두 작업은 각각 새 확인을 요구합니다.

외부 계정·리소스, Chat·작업 이력은 이 화면으로 삭제되지 않습니다. PAT가 외부에서 계속 유효할 수 있으므로 공급자에서 별도 폐기를 확인합니다. 공급자 권한 철회 실패와 로컬 해제 성공은 동시에 존재할 수 있습니다. 결과 불명에서는 동일 해제/삭제 요청을 반복하지 않고 정확한 연결을 새로 읽습니다.

일반 사용자: 현재 대화의 연결 선택

현재 열려 있는 일반 Chat에서 사용할 연결을 명시적으로 선택할 수 있습니다. 선택 화면의 기본값 안내만으로 자동 선택됐다고 판단하지 않습니다. 확인 창에서 세션 ID와 연결 ID를 읽고 한 번 확정합니다. 응답 뒤 해당 세션·프로젝트, 증가한 revision, 공급자 바인딩과 실제 세션 해석이 모두 같은 대상을 가리키는지 다시 확인합니다. 다른 대화나 프로젝트로 이동하면 예전 확인을 사용하지 않습니다.

선택만으로 공급자 요청·작업 실행은 일어나지 않습니다. 연결에 사용 권한이 없거나 저장 상태가 바뀌면 실제 요청에서 차단될 수 있습니다. 응답이 유실됐을 때도 같은 선택을 자동 반복하지 않습니다.

관리자: 사용 위치와 기본 연결

연결 사용 위치 · 기본 연결에서 연결별 Console·Remote Request·채널·예약 사용 위치와 모든 프로젝트/선택 프로젝트 범위를 확인합니다. 사용 위치를 모두 해제하면 어느 실행 경로에서도 후보로 사용할 수 없습니다. 프로젝트 ID는 정확히 입력해야 하며 저장된 ID만으로 해당 프로젝트가 실제 존재한다고 보장하지 않습니다.

별도 Worker·Project 기본 연결은 공급자별 기본 선택 순서를 관리합니다. Worker 기본값은 Console 사용과 모든 프로젝트 범위가 필요합니다. Project 기본값은 해당 프로젝트에서 사용할 수 있어야 합니다. 현재 대화의 명시적 선택이 먼저 적용됩니다. 기본값을 삭제하면 다른 기본값이나 단일 가용 후보로 돌아갈 수 있으므로 연결 사용을 완전히 금지하려면 정책도 확인해야 합니다. 변경 전후 확인 창의 ID·범위·revision과 canonical readback을 대조합니다. 이 설정은 외부 계정의 scope나 작업 권한을 추가하지 않습니다.

관리자: RRA 대상 Worker 설정

연결 목록 → RRA 대상 Worker는 외부 서비스 연결과 별도인 서버 소유 대상 설정입니다. 관리자는 대상의 HTTPS origin, 예상 Worker/instance, 표시 이름, 사용 여부와 현재 busy 상태를 읽고 정확한 대상을 선택합니다. 등록·수정/자격 교체·삭제는 각각 확인과 revision 검사를 거친 뒤 동일 ID의 최종 상태를 다시 읽습니다. 비밀 자격은 입력 후 다시 표시되지 않습니다. 사용 중인 대상은 비활성화·교체·삭제가 차단될 수 있습니다.

대상을 켜도 요청은 자동 전송되지 않습니다. 개발 워커는 대상 조회·미리보기, Console의 요청별 1회 승인, 상태·결과 대조를 수행해야 합니다. 대상 Worker는 자체 인증·정책으로 다시 입장 여부를 판정하고 호출 Worker의 권한을 물려받지 않습니다. 새 설정은 RRA HTTP v1 요청 본문이나 세션을 이어 대화하는 방법을 변경하지 않습니다. 운영 대상의 실제 도달·자격·승인·응답은 별도 테스트입니다.

로그인 401·권한 403보호된 연결·토큰 입력을 지우고 계정과 관리자 역할을 확인합니다. 공급자 자체 401/403은 Console 로그아웃으로 오해하지 않습니다.
revision 충돌·대상 없음정확한 ID의 최신 상태를 다시 읽고 새 결정을 합니다. 같은 이름의 다른 연결로 자동 전환하지 않습니다.
결과 불명·readback 불일치POST/PUT/DELETE를 반복하지 않습니다. 정확한 대상·revision·감사 상태와 실제 결과를 관리자에게 대조합니다.
설정됨·인증 대기외부 계정 확인, 사용 위치, 실제 요청 승인과 결과를 별도로 시험합니다.

직접 테스트와 화면 캡처

  1. 정확한 이미지가 적용된 시험 Worker에서 관리자/일반 사용자로 연결 목록과 변경 버튼 권한을 비교합니다.
  2. 가상 연결 두 개를 같은 이름으로 만들어 ID가 다르고 인증이 자동 완료되지 않는지 확인합니다. 정확한 시험 연결만 삭제·복원합니다.
  3. 시험 계정으로 인증·계정 확인·현재 Chat 선택·정책/기본값을 각기 별도 재조회합니다. 실제 외부 계정 호출은 승인된 경우에만 결과를 판정합니다.
  4. RRA 시험 대상의 등록/사용 중 차단/설정 삭제와 요청별 승인·후속 대화를 분리하여 검증합니다. 실제 대상 요청은 승인된 두 워커에서만 수행합니다.
  5. 데스크톱과 모바일에서 정확한 이미지의 목록·상세·확인·오류 화면을 민감값 없이 촬영합니다.

화면 미촬영 · 이 후보의 실제 운영 연결 화면은 확보되지 않았습니다. 로컬 소스 검사 통과를 실제 제공자 수용으로 바꾸어 기록하지 않습니다. 390px 로컬 합성 화면에서는 긴 연결 ID와 설명의 오른쪽 잘림이 확인되어 모바일 재검증이 필요합니다.

시작 조건

정확한 후보 이미지가 적용된 시험 워커의 관리자·일반 사용자, 시험 연결과 RRA 대상, 외부 계정 사용 승인 범위를 준비합니다.

실행 순서

  1. 연결 목록에서 같은 이름의 두 ID를 구분하고 관리자/일반 사용자 버튼 권한을 비교합니다.
  2. 시험 연결 하나의 인증·상태 확인·정보 수정·현재 Chat 선택·사용 위치/기본값을 각기 별도 재조회합니다.
  3. RRA 대상 설정과 요청별 승인·후속 대화를 분리하여 확인합니다.
  4. 해제·삭제와 결과 불명에서 정확한 연결만 변경하고 자동 중복 요청이 없는지 봅니다.
  5. 데스크톱·모바일 화면을 촬영하되 토큰·코드·계정은 가립니다.

통과 기준

연결 구성, 제공자 인증, 현재 대화 선택, 정책, RRA 승인과 대상 결과가 각각 별도로 판정됩니다.
