어떤 권한을 따르는가

GitLab·GitHub에서 수행할 수 있는 외부 작업과 접근할 수 있는 프로젝트·저장소는 연결된 서비스 계정과 토큰에 실제 부여된 권한을 따릅니다. 이 후보에서는 Git 연결 생성·수정에 예전의 기능 체크박스와 외부 리소스 허용목록을 사용하지 않습니다. 그러나 워커의 사용자 요청 권한, 정확한 연결 계정·서비스 주소, 사용 중지·연결 해제, 사용 경로와 프로젝트 사용 범위, 읽기 전용 요청과 변경 승인, 비밀정보 보호는 계속 적용됩니다.

프로젝트 사용 범위는 이 연결을 선택할 수 있는 Worker 프로젝트를 뜻합니다. GitLab 프로젝트나 GitHub 저장소의 외부 허용목록이 아닙니다. 화면에서 연결이 보이거나 사용 준비 완료라고 표시돼도 토큰의 모든 서비스 권한을 확인했다는 뜻은 아닙니다. 일반 사용자는 관리자가 배정한 준비된 연결 중 현재 대화에서 사용할 계정을 고를 수 있으며, 서비스 설정·토큰·전환은 관리자 작업입니다.

새 GitLab·GitHub 연결 만들기

  1. 관리자 계정에서 설정 → 커넥터를 열고 연결 가능한 서비스에서 GitLab 또는 GitHub를 선택합니다. GitLab 회사 서버를 쓰는 경우 서비스 및 OAuth 애플리케이션의 GitLab 서버 URL을 HTTPS 서비스 주소로 확인합니다. 토큰 값이나 내부 주소를 대화에 입력하지 않습니다.
  2. 연결 계정 추가에서 연결 이름과 인증 방식을 고릅니다. GitLab Access Token 방식은 Access Token 입력 뒤 연결 만들기로 생성·토큰 저장·계정 확인을 순서대로 요청합니다. GitHub 등 다른 인증 방식은 화면에 표시된 기기 코드·브라우저 OAuth 또는 토큰 절차를 사용합니다.
  3. 사용 경로와 프로젝트 사용 범위를 선택합니다. 이는 워커에서 어디에 연결을 배정할지에 관한 설정입니다. 외부 저장소 권한을 확대하거나 제한하는 설정으로 해석하지 않습니다.
  4. 저장 안내와 연결 카드의 계정·자격증명 설정됨·사용 준비 완료 상태를 재조회합니다. 연결 확인으로 계정 확인을 요청하고, 승인된 시험 프로젝트의 실제 읽기 응답을 원본과 대조한 뒤에만 업무 사용을 판정합니다. 저장이 실패하면 상세 화면의 오류 안내를 읽고 입력 초안을 확인합니다.

기존 연결을 관리자가 전환하기

기존 Git 연결은 자동으로 바뀌지 않습니다. 카드에 기존 권한 정책 연결입니다가 보이면 예전 기능·외부 리소스 제한이 아직 적용됩니다. 관리자와 일반 사용자 모두 이 상태를 확인할 수 있지만 전환은 관리자에게만 표시됩니다.

  1. 관리자는 전환 대상의 서비스·계정·토큰 권한과 기존 사용 경로·프로젝트 배정을 확인합니다. 예전 체크박스의 기본값이나 해제 상태만으로 관리자의 의도를 추측하지 않습니다.
  2. 계정/토큰 권한 방식으로 전환을 선택하고 확인 창에서 외부 작업·리소스의 권한 기준이 바뀐다는 내용을 읽습니다. 확인하면 기존 연결 ID·자격증명·사용 경로는 유지되며, 실행 중인 요청의 권한은 확장되지 않습니다.
  3. 카드가 GitLab·GitHub 권한은 연결한 계정과 토큰에 실제로 부여된 권한을 따릅니다로 바뀌었는지 다시 읽습니다. 계정·준비 상태·실제 서비스 응답을 각각 검사합니다. 전환 자체가 서비스 토큰의 권한을 늘리거나 OAuth 동의를 갱신하지는 않습니다.

OAuth 범위와 재인증 확인하기

OAuth 연결에는 다음 인증의 기본 OAuth 요청 범위와 현재 토큰에 보고된 OAuth 범위가 따로 표시됩니다. 관리자가 다음 인증에서 요청할 서비스 OAuth 범위를 변경해도 그 즉시 권한이 바뀌지 않습니다. 서비스 자체의 범위를 확인한 뒤 브라우저로 연결 또는 기기 코드로 연결을 시작하고, 동의 후 상태 확인과 보고된 범위를 다시 읽습니다. GitLab 기본 요청 api, GitHub 기본 요청 read:user repo는 모든 관리자 API 권한을 보장하지 않습니다.

일부 범위만 허용해도 계정 확인은 성공할 수 있지만 필요한 작업은 제공자에서 거부될 수 있습니다. 보고된 범위가 비어 있으면 전체 권한으로 해석하지 마세요. PAT 권한은 해당 서비스에서 관리하고, 토큰을 바꿀 때는 관리자 화면의 입력 전용 필드로 저장한 뒤 계정 확인과 실제 요청을 다시 수행합니다.

실제 제공자 거부를 확인하기

먼저 현재 워커 이미지와 선택된 연결·계정·서비스 주소, 사용 중지·회수 여부, 워커 프로젝트·사용 경로를 확인합니다. 연결 상태가 정상인데 GitLab·GitHub가 401 또는 403을 반환했다면 서비스의 계정·토큰·OAuth 동의와 대상 리소스 권한을 확인합니다. 같은 토큰을 다른 경로로 보내는 것으로 거부가 해결됐다고 가정하지 않습니다. 404만으로 권한 부족이나 자료 부재를 단정하지 않습니다. 실제 제공자 결과와 Task 최종 상태를 대조하고, 새 권한이 필요하다면 서비스에서 허용한 뒤 재인증·재확인합니다.

읽기 전용 요청에서 쓰기를 시도하지 않는지 확인하고, 변경 작업은 승인된 시험 자료에서만 한 번 실행합니다. 결과 불명 쓰기는 다른 경로나 새 Task로 자동 재전송하지 말고 원래 리소스의 효과를 먼저 조회하세요. 기능 안내 스킬이나 Wiki 문서가 계정 권한을 주지는 않습니다.

이전 이미지로 되돌릴 때

앞선 GitLab REST fallback 이미지는 새 계정 권한 방식을 알지 못합니다. 기존 연결 자료의 읽기는 보존되지만, 이전 이미지에서 어느 커넥터 설정이든 저장하면 새 권한 방식의 표시 목록이 사라집니다. 다시 이번 이미지로 올린 뒤에는 관리자가 영향받은 Git 연결을 명시적으로 재전환해야 합니다. 이번 이미지에서 새로 만든 연결은 이전 이미지에서 같은 사용성을 보장하지 않습니다. 이전 버전으로 되돌리기는 계정 권한이나 진행 중 작업의 완전한 복원이 아닙니다.

되돌리기 전후로 연결·계정·사용 위치·보존 기록과 진행 중 쓰기 결과를 대조하고 운영 담당자와 절차를 결정합니다. 불확실한 변경을 새 요청으로 재실행하지 않습니다. 로컬의 정확한 이전 이미지 저장소 읽기/쓰기 검사는 통과했지만, 운영 워커에서 되돌리기를 실행하거나 전체 연결을 실제로 전환한 결과는 아직 없습니다.

화면 증거와 남은 검사

위 세 장은 실제 후보 소스의 설정 컴포넌트·스타일을 로컬 Chromium에서 모의 API로 렌더링했습니다. 한국어·영어의 360/390/1280픽셀 여섯 경우에서 새 연결·전환·OAuth 범위·저장 오류·일반 사용자 읽기 전용·좁은 화면 정렬을 검사했습니다. 새 이미지의 운영 화면 캡처와 실제 GitLab·GitHub 계정 결과는 미확보입니다. 적용 뒤에는 워커의 정확한 실행 이미지·시각, 관리자/일반 사용자 화면, 연결 상태와 제공자 원본 결과를 비밀값을 가린 실제 캡처로 보완합니다.

시작 조건

계정 권한 방식 후보를 정확히 실행하는 승인된 시험 워커, 관리자·일반 사용자 계정과 서비스의 격리 시험 프로젝트가 필요합니다. 22:28(KST)에는 새 이미지 제안까지만 확인됐으므로 운영 결과는 미실행입니다. 페이지 화면은 로컬 Chromium·모의 API 자료입니다.

실행 순서

  1. 관리자/일반 사용자로 설정 → 커넥터를 열어 GitLab·GitHub의 계정·서비스 주소·편집 가능 범위와 한국어/영어 390픽셀·데스크톱 화면을 비교합니다.
  2. 관리자가 새 시험 연결을 만들고 저장 안내·연결 확인·실제 제공자 읽기 결과를 대조합니다. 외부 기능 체크박스나 저장소 허용목록이 다시 나타나지 않아야 합니다.
  3. 예전 제한이 있는 기존 연결을 관리자 확인 전후로 비교하고 연결 ID·계정·자격증명·사용 위치 보존과 일반 사용자 전환 불가를 검사합니다.
  4. 부분/빈 OAuth 동의와 실제 401·403, 재인증 후 부여 범위·제공자 결과를 비교합니다. 404만으로 권한 부족을 단정하지 않습니다.
  5. 읽기 전용·승인된 쓰기와 결과 불명 중복 차단은 격리 시험 자료에서 검사하고, 이전 이미지 설정 저장 뒤 재업그레이드·재전환은 복제한 상태에서만 확인합니다.
